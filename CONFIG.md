# Repository policy

`repos.json` is the durable policy. Each entry has a positive integer GitHub repository `id`, exact `full_name`, and boolean `enabled`. IDs and names must be unique (names case-insensitively); malformed policy fails closed. Copy `repos.example.json` to the ignored `repos.json` and replace the example with the actual repository ID and name. Verify IDs independently using `gh api --method GET repos/OWNER/REPO --jq '{id,full_name}'` before adding repositories.

The receiver uses `REPO_CONFIG` (default `repos.json`) instead of `ALLOWED_REPOS`. Pass the same path as the required `repos` argument to `Worker` and `GitHubReadOnly`. It is re-read for authorization, so a disabled entry stops subsequent checks. Update the file atomically in a trusted directory; this policy is security-sensitive. A rename or transfer requires explicitly updating `full_name` while retaining the verified ID; queued events with the old name will be skipped. Name matching is exact. The GitHub adapter also verifies the PR API's base repository ID, preventing a reused name from authorizing a different repository. Configuration changes are not atomic with an already-running model call; stop workers before changing policy if a hard cutoff is required.

For installation inventory synchronization, the receiver's `PUBLICATION_GATE` must name the same local gate directory as the worker/orchestrator `--publication-gate`, and `REPO_CONFIG` must be the same policy. Configure the receiver with the pinned installation and App read credentials as well. Without the shared gate, receiver signals do not stop publication; see ORCHESTRATOR.md for pending-signal recovery and GitHub snapshot limitations.

For App webhooks, set `GITHUB_APP_INSTALLATION_ID` to a positive decimal integer below 2^63. If `installation` is present, `installation.id` must be that exact integer; a missing field is accepted as a legacy repository hook. An invalid setting fails startup. If unset, installation identity is not checked. Anyone knowing the shared secret can omit `installation` and impersonate a legacy hook; HMAC and repository policy, not installation identity, authorize such requests. Signed and authorized events are deduplicated by delivery ID, exact body, and, when sufficient revision fields are present, semantic PR identity; see INGRESS.md for the fallback and limitations.

기본은 dry-run이며 명시적인 single-VPS MVP 모드에서 설정된 저장소에 게시할 수 있다. 유효한 gate와 정확한 결과에 대한 수동 승인 또는 해당 저장소의 명시적 `auto_repos` 사전 승인이 필요하다. 사전 승인 시 개별 리뷰 승인은 필요하지 않다. 단일 계정은 운영상 우회를 막는 보안 경계가 아니며 이전 게시 프로세스 및 코드 외부의 직접 GitHub POST를 차단하지 못한다.

The gate requires `gate_path`, an absolute path to a dedicated local POSIX directory owned by the effective administrator UID with mode 0700, containing a persistent, administrator-owned 0600 regular file named `lock`. All path ancestors must be owned by root or that UID and not group/other writable; symlinks, hard-linked lock/state files, unsafe permissions, missing/legacy evidence, and lock timeouts fail closed. Never replace or delete `lock`, the directory, or its ancestors while any process is running. All publishers and policy/approval writers must use the very same directory and filesystem; no NFS or independent hosts. Stop old publishers before use. The gate currently runs publishers and writers under the same effective UID: that UID and everyone able to act as it must be fully trusted administrators. It does not enforce separation from the publishing process or protect against direct filesystem/API modifications, alternative gate paths, monkeypatching or direct GitHub POSTs. The explicit MVP mode accepts these risks; independent isolation is a recommended upgrade.

Publication policy is the gate's `policy`, not `repos.json`: the latter remains an additional check, and editing it is not a synchronized publication revocation. For administration, `revocation_gate.gate_snapshot(path)` returns `(state, version)`; `update_gate(path, policy, approvals, expected=version, auto_repos=...)` atomically replaces all state under the shared lock, rejecting a stale version. For initial creation only, call `update_gate` with `expected=None`. Policy maps decimal repository ID strings to exact repository names. Each manual approval is `[repo_id, full_name, pr_number, head_sha, base_sha, sha256_hex]`, where the hash is SHA-256 of the exact UTF-8 review before the publication marker. The optional `auto_repos` explicitly preauthorizes matching policy ID/name pairs in single-VPS mode; omission disables it. To stop all publication remove both automatic policy and manual approvals, or remove the repo from policy. Never treat the callback as approval evidence. State and lock must be created and updated only by trusted administrators using this API; provisioning the directory and lock is an explicit administrative operation, not performed by the publisher.

The same exclusive OS lock covers gate authorization, final PR checks and the entire POST; a policy or approval revocation completes only after it acquires the lock and the new state is durably committed. A POST already in progress finishes first, or may have an uncertain outcome on crash/timeout. A crashed process releases its lock, but its durable pending claim prevents automatic repost; reconcile uncertain GitHub delivery manually. An fsync failure after replacement means the outcome of the update is uncertain: re-read the gate before acting. GitHub state may change independently after the final check; this lock cannot provide atomicity with GitHub. Bound transport timeouts operationally so revocation does not wait indefinitely; lock acquisition itself times out after five seconds. Do not fork while holding the lock.

Separate publishing accounts remain a recommended hardening step, not an MVP prerequisite. Publication tokens are repository-scoped and limited to pull_requests write. Results lacking their original repository ID cannot be published and must be regenerated; never infer it from a queued event.
