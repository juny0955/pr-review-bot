# Repository policy

`repos.json` is the durable policy. Each entry has a positive integer GitHub repository `id`, exact `full_name`, and boolean `enabled`. IDs and names must be unique (names case-insensitively); malformed policy fails closed. Copy `repos.example.json` to the ignored `repos.json` and replace the example with the actual repository ID and name. Verify IDs independently using `gh api --method GET repos/OWNER/REPO --jq '{id,full_name}'` before adding repositories.

The receiver uses `REPO_CONFIG` (default `repos.json`) instead of `ALLOWED_REPOS`. Pass the same path as the required `repos` argument to `Worker` and `GitHubReadOnly`. It is re-read for authorization, so a disabled entry stops subsequent checks. Update the file atomically in a trusted directory; this policy is security-sensitive. A rename or transfer requires explicitly updating `full_name` while retaining the verified ID; queued events with the old name will be skipped. Name matching is exact. The GitHub adapter also verifies the PR API's base repository ID, preventing a reused name from authorizing a different repository. Configuration changes are not atomic with an already-running model call; stop workers before changing policy if a hard cutoff is required.

현재 운영 정책: 실제 게시는 코드 최상위 안전 잠금으로 무조건 차단되며 `enabled=True`, 유효한 gate와 승인으로도 활성화할 수 없다. 기본 dry-run은 유지된다. 게시자와 관리자 계정의 분리 및 `repos.json`·승인 변경 우회 방지가 구현되고 별도 운영 격리가 명시적으로 검증되기 전에는 잠금을 해제하지 않는다. 이전 버전 프로세스와 코드 외부의 직접 GitHub POST는 이 잠금이 차단하지 못하므로 이전 게시 프로세스는 중지해야 한다.

The following gate describes development behavior, not permission to publish or deploy. It requires `gate_path`, an absolute path to a dedicated local POSIX directory owned by the effective administrator UID with mode 0700, containing a persistent, administrator-owned 0600 regular file named `lock`. All path ancestors must be owned by root or that UID and not group/other writable; symlinks, hard-linked lock/state files, unsafe permissions, missing/legacy evidence, and lock timeouts fail closed. Never replace or delete `lock`, the directory, or its ancestors while any process is running. All publishers and policy/approval writers must use the very same directory and filesystem; no NFS or independent hosts. Stop old publishers before use. The gate currently runs publishers and writers under the same effective UID: that UID and everyone able to act as it must be fully trusted administrators. It does not enforce separation from the publishing process or protect against direct filesystem/API modifications, alternative gate paths, monkeypatching or direct GitHub POSTs. Do not deploy until those bypasses are operationally prevented and account separation is implemented.

Publication policy is the gate's `policy`, not `repos.json`: the latter remains an additional check, and editing it is not a synchronized publication revocation. For administration, `revocation_gate.gate_snapshot(path)` returns `(state, version)`; `update_gate(path, policy, approvals, expected=version)` atomically replaces both under the shared lock, rejecting a stale version. For initial creation only, call `update_gate` with `expected=None`. Policy maps decimal repository ID strings to exact repository names. Each approval is `[repo_id, full_name, pr_number, head_sha, base_sha, sha256_hex]`, where the hash is SHA-256 of the exact UTF-8 review before the publication marker. Never treat the callback as approval evidence. State and lock must be created and updated only by trusted administrators using this API; provisioning the directory and lock is an explicit administrative operation, not performed by the publisher.

The same exclusive OS lock covers gate authorization, final PR checks and the entire POST; a policy or approval revocation completes only after it acquires the lock and the new state is durably committed. A POST already in progress finishes first, or may have an uncertain outcome on crash/timeout. A crashed process releases its lock, but its durable pending claim prevents automatic repost; reconcile uncertain GitHub delivery manually. An fsync failure after replacement means the outcome of the update is uncertain: re-read the gate before acting. GitHub state may change independently after the final check; this lock cannot provide atomicity with GitHub. Bound transport timeouts operationally so revocation does not wait indefinitely; lock acquisition itself times out after five seconds. Do not fork while holding the lock.

Operational deployment requires a separate publishing account with minimum GitHub permissions and repository access, independent of the read/model account. This code does not enforce account separation or permissions. Results lacking their original repository ID cannot be published and must be regenerated; never infer it from a queued event.
