# 로컬 PR 웹훅 수신 프로토타입

실험용 Python 프로토타입입니다. `127.0.0.1`에서 서명된 GitHub `pull_request` 페이로드를 수신하고, 저장소 ID 및 이름 허용 목록을 확인한 뒤 응답하기 전에 원본 페이로드를 SQLite에 저장합니다. 오프라인 테스트는 표준 라이브러리를 사용하며, 선택적으로 사용하는 실험용 어댑터는 GitHub와 모델 제공자에 접근할 수 있습니다. 프로덕션 배포 구성이나 공개 엔드포인트는 포함되어 있지 않습니다.

## 실행

`repos.example.json`을 Git에서 무시되는 `repos.json`으로 복사하고, `CONFIG.md`의 설명에 따라 저장소 ID와 이름을 설정하세요. 안전한 환경 변수 관리를 통해 강력한 시크릿을 설정하세요. 시크릿을 커밋하거나 실험에 프로덕션 시크릿을 사용하지 마세요.

```sh
export WEBHOOK_SECRET  # supply via your secret manager or secure prompt
export REPO_CONFIG='./repos.json'
export QUEUE_DB='./queue.sqlite3'  # optional
export PORT=8080                  # optional
python3 receiver.py
```

`python3 -m unittest -v`로 테스트를 실행하세요.

`POST /webhook`은 최대 1 MiB 크기의 본문을 받아 정확한 원본 바이트에 대해 `X-Hub-Signature-256`을 검증하고, 이벤트, 저장소, 지원되는 액션 및 PR 필드를 확인한 다음 직렬화된 트랜잭션으로 삽입합니다. 최초 전달에는 202를 반환합니다. 바이트가 동일한 반복 전달에는 전달 ID가 달라도 200을 반환하고, 기존 ID를 다른 바이트와 함께 재사용하면 409를 반환합니다. 지원되지 않는 이벤트와 잘못된 요청은 거부됩니다. 큐에 행이 1,000개 있으면 새 본문을 삽입하기 위해 보존 조건을 충족한 오래된 완료 항목 하나를 삭제할 수 있으며, 삭제할 항목이 없으면 503을 반환합니다. 중복 전달은 큐가 가득 차도 정상 응답합니다. DB는 권한 모드 0600으로 생성되거나 제한되며 심볼릭 링크여서는 안 됩니다. 비공개로 유지되는 신뢰할 수 있는 디렉터리를 사용하고 사이드카 파일과 백업을 보호하세요. 페이로드에는 민감한 저장소 데이터가 포함될 수 있습니다.

## 오프라인 워커

`worker.Worker(db_path, github, model, wiki, repos)`는 `run_once()`로 기존 전달 하나를 처리합니다. 신뢰할 수 있는 테스트 대역만 주입하세요. `github.current(repo, number)`는 `state`, 불리언 `draft`, head `sha`, `base_sha`를 반환합니다. `github.diff(repo, number, sha, base_sha)`는 지정된 head와 base에 고정된 PR diff 텍스트를 반환해야 합니다. 가변 PR diff를 가져오기 전후로 SHA를 확인하는 것만으로는 중간에 변경되었다가 복원되는 경우(ABA)를 배제할 수 없습니다. 제공된 GitHub 어댑터는 임시 bare 저장소에 base SHA와 `refs/pull/<번호>/head`를 가져오고 head SHA를 검증한 뒤, 정확히 하나인 merge-base와 head 사이의 diff를 생성합니다. 파일을 체크아웃하지 않으며 외부 diff와 textconv를 사용하지 않습니다. 이는 현재 지정된 base/head의 merge-base 기준 로컬 Git diff이지 GitHub PR 화면의 역사적 merge-base, rename 표시 또는 기타 렌더링과 동일함을 보장하지 않습니다. SHA나 merge-base를 확인할 수 없거나 제한을 초과하면 실패합니다. Git 및 gh 인증이 필요합니다. 임시 Git 저장소를 사용하려면 아래의 제한된 `PR_DIFF_TMPDIR` 마운트가 필요합니다. `model.review(request)`는 텍스트를 반환합니다. 리뷰는 공백만으로 이루어져서는 안 되며 UTF-8 기준 65,536바이트를 넘을 수 없습니다. 실행 가능한 예제는 `test_worker.py`를 참조하세요. wiki 경로는 직접 사용하는 볼트로 설정하세요. 테스트는 임시 픽스처를 사용합니다. 요청에는 의도된 프로필 `prreview`와 모델 `gpt-6.1-terra`가 표시되지만, Hermes를 시작하거나 프로필 격리를 강제하지는 않습니다. 결과는 검증된 `base_sha`를 포함하여 SQLite의 `work.result`에 로컬 JSON으로 저장되며, 리뷰는 게시되지 않습니다. 명시적으로 활성화하는 게시자는 호출자가 리뷰 생성에 사용된 `base_sha`를 키워드 인자로 제공하도록 요구하며, 형식과 현재 PR의 base 일치 여부만 확인합니다. 전달된 값이 실제 저장된 워커 결과에서 왔는지 또는 리뷰와 연결되는지는 검증하지 않으므로 호출자가 이를 보장해야 합니다. base가 누락되면 거부합니다. 게시 원장의 새 키에는 base가 포함되며, 같은 SQLite 트랜잭션에서 이전 버전의 키도 예약해 이전 버전의 중복 게시 클레임을 막습니다. 모든 버전은 동일한 내구성 있는 원장을 공유해야 합니다. 이전 v2 기록이 있는 원장은 각 항목을 새 코드로 처리하기 전에는 예약이 없을 수 있으므로 구버전을 함께 실행하기 전에 별도 이관 또는 중단이 필요합니다. base 정보가 없는 이전 원장 기록은 게시 여부나 마커와 관계없이 `ambiguous`로 처리하고 자동으로 다시 게시하지 않으므로 운영자의 확인이 필요합니다. 게시 전 확인과 실제 게시 사이의 변경은 원자적으로 막지 못합니다. 워커는 PR 코드를 체크아웃하거나 임포트하거나 실행하지 않습니다.

설정된 저장소의 열린 비초안 PR에 대한 적격 이벤트와 정확히 40자인 head SHA만 허용됩니다. 리뷰 전후로 현재 PR 상태를 확인합니다. 작업 클레임은 직렬화되고 리스와 펜싱으로 관리되며, 실패한 작업은 재시도되고 만료된 클레임은 복구할 수 있습니다. 처리는 최소 한 번 수행되므로 리스가 만료되면 어댑터 호출이 중복될 수 있습니다. 각 전달의 클레임은 만료된 리스를 포함해 최대 세 번입니다. 재시도 지연 시간은 30초와 60초이며 SQLite에 저장됩니다. 만료된 리스의 지연 시간은 만료 시점부터 시작됩니다. 마지막 실패 또는 마지막 리스 만료 후에는 행이 `failed` 상태가 되어 운영자의 개입이 필요합니다. 이전 스키마의 기존 재시도 행은 재시도 횟수를 이미 소진하지 않았다면 즉시 처리 대상이 됩니다. 지연 중인 행은 나중에 들어온 처리 가능한 전달을 막지 않습니다. 시간 계산은 일관된 시스템 시계에 의존합니다. 마지막 최신성 확인과 이후 변경은 원자적으로 이루어지지 않습니다. Wiki 검색은 설정된 볼트의 `wiki/`가 있으면 그 디렉터리, 없으면 설정 디렉터리의 최상위 Markdown만 읽습니다(재귀 및 인덱스 링크 추적 없음). 경로 구성요소와 파일의 심볼릭 링크를 거부하고, 열린 파일의 읽기 전후 메타데이터와 경로를 비교해 변경이 감지되면 제외합니다. 읽을 수 있는 `index.md`의 첫 청크를 우선 보존합니다. 디렉터리 항목이 500개를 초과하면 임의의 불안정한 부분집합 대신 인덱스 첫 청크만 반환합니다. 나머지는 파일당 앞 256 KiB, 총 4 MiB까지 읽어 최대 16 KiB UTF-8 청크로 나누고 diff 키워드 중복도, 파일명, 청크 순서로 정렬합니다. 최대 20개 청크(총 텍스트 320 KiB)를 반환하므로 같은 경로가 반복될 수 있습니다. 읽은 범위의 잘못된 UTF-8은 해당 파일을 제외하고 잘린 범위의 불완전한 마지막 문자는 버립니다. 2초 기한은 작업 사이에 확인하는 최선의 제한이며 블로킹 파일시스템 호출이나 순위 처리 자체를 중단하지 못합니다. 시간 제한, 읽기 예산, 파일 앞부분만 검색하는 방식 및 청크 경계 때문에 관련 내용이 누락될 수 있고 시간 제한에 도달하면 결과가 실행마다 다를 수 있습니다. 반환 직전 디렉터리 선택 정책과 선택된 파일의 식별자 및 메타데이터를 다시 검사하고 변경이 감지되면 결과 전체를 버립니다. 검사는 원자적이지 않아 검사 후 변경이나 변경 후 복원되는 ABA 레이스를 완전히 차단할 수 없으며 신뢰할 수 있는 로컬 파일시스템과 상위 디렉터리 관리가 필요합니다. Wiki 내용과 PR 텍스트는 신뢰할 수 없습니다. SQLite DB와 사이드카 파일 및 디렉터리를 보호하세요. 결과에는 민감한 정보가 포함될 수 있습니다.

샌드박스나 프롬프트 인젝션 격리는 구현되어 있지 않으며, 어댑터는 코드를 실행하거나 네트워크에 접근할 수 있습니다. 프로덕션용 스케줄러, 보존 정책 또는 모니터링은 제공되지 않습니다. 기본값은 게시 비활성화이며, 제한된 단일 VPS MVP에서는 운영자가 정확한 결과를 확인하고 승인한 뒤 게시할 수 있습니다. 설정과 잠금, 잔여 위험은 ORCHESTRATOR.md를 참조하세요. 최신성 검사와 게시 사이의 변경은 원자적으로 막지 못합니다.

실험적 큐 보존: done/failed/skipped 결과는 완료 후 최소 7일 보존하며, 큐가 찼을 때만 삭제 조건을 충족한 만료 결과 중 가장 오래된 것 하나를 삭제하고 전달 ID와 본문 SHA-256 tombstone을 남깁니다. 만료된 결과는 백업되지 않았다면 복구할 수 없습니다. 대기·재시도·실행 중 작업, 완료 시각이 없는 결과, 연결된 outbox에 `sent`가 아닌 항목이 있는 결과는 삭제하지 않으며, 정리할 항목이 없으면 503으로 재시도를 요구합니다. 시계 오류는 보존 기간에 영향을 줍니다. Tombstone은 무기한 증가하고 SQLite 파일도 축소가 보장되지 않아 디스크가 무한 증가하거나 가득 찰 수 있습니다. 운영자는 디스크 사용량을 감시하고 안전한 백업 및 용량 계획을 마련해야 합니다. DB를 삭제하거나 오래된 백업으로 복원하면 이후 재전송 중복 방지 기록이 사라집니다. 이 정책은 프로덕션용 보존·감사 체계를 대체하지 않습니다.

`resolve_hermes_direct_adapter()`는 활성 프로필이 prreview인 경우 정상 Hermes 인증 경로로 gpt-6.1-terra를 사용합니다. 프로필은 보안 샌드박스가 아니며 공유 인증으로 fallback할 수 있습니다: https://hermes-agent.nousresearch.com/docs/user-guide/profiles. `DirectInferenceAdapter`는 신뢰할 수 있는 클라이언트를 직접 주입하는 실험용 어댑터이며 wiki가 비어 있어도 `authorize_wiki_transfer=True`가 필요합니다. 이는 인증 경계가 아닙니다. 프롬프트 인젝션 방어는 보장되지 않고 출력은 신뢰할 수 없습니다. 명시적 단일 VPS MVP의 검토 후 승인 게시 외에는 자동 게시하지 마세요. 테스트는 mock만 사용합니다.

## Git diff 임시 저장소 요구 사항

관리자가 Linux에 전용 tmpfs를 미리 마운트하고 `PR_DIFF_TMPDIR=/run/pr-review-bot-diff`를 설정해야 합니다. 다른 경로는 허용되지 않습니다. `/`와 `/run`은 root 소유이고 그룹/기타 쓰기가 금지되어야 하며, 마운트 지점은 워커의 유효 UID 소유이고 그룹/기타 접근이 없어야 합니다. 심볼릭 링크를 거부하고 열린 디렉터리에서 tmpfs 유형과 전체 용량(0 초과, 최대 256 MiB)을 확인합니다. 조건을 충족하지 않으면 diff 생성은 실패합니다.

보안 가정: root, 마운트 네임스페이스와 `CAP_SYS_ADMIN` 보유자, 워커와 같은 UID의 모든 프로세스는 신뢰합니다. 이들이 경로를 교체하거나 하위 마운트를 만들지 않아야 합니다. `/run`이 비특권 사용자에 의해 변경되지 않고 비공개 마운트는 다른 UID가 변경할 수 없으므로 Git이 사용하는 경로를 보호합니다. 동일 UID나 특권을 가진 악의적인 프로세스에 대한 샌드박스가 아닙니다.

워커 계정만 접근할 수 있는 비공개 마운트를 사용하고, 생성과 마운트 권한 및 용량은 운영자가 관리하세요. 코드는 스크래치 루트 아래의 중첩 마운트나 실행 중 마운트 변경을 검사하지 않습니다. 운영자는 해당 경로 아래에 중첩 마운트가 없고 신뢰할 수 없는 주체가 마운트 구성을 변경할 수 없도록 보장해야 합니다. 마운트의 용량 제한은 그 파일시스템 전체에 적용되므로 동시 작업이나 다른 사용자가 공간을 공유하면 실패할 수 있습니다. 임시 저장소에는 민감한 Git 객체가 포함될 수 있으며 tmpfs는 환경에 따라 스왑될 수 있습니다. 이 제한은 샌드박스, 자격 증명 격리 또는 시스템 전체 메모리·디스크 사용량 제한이 아닙니다. Git 실행에는 별도로 파일당 64 MiB, 전체 실행 시간 60초, 프로세스 주소 공간 1 GiB 등의 제한이 적용되며 큰 저장소나 diff는 실패할 수 있습니다.

## GitHub App 인증 실험 모듈

`github_app_auth.InstallationAuth(app_id, installation_id, key_path, repos, purpose, transport)`는 단일 허용 저장소의 설치 토큰을 요청합니다. `read`는 pull requests와 contents 읽기, `publish`는 pull requests 쓰기를 요청합니다(자동 부여 metadata 읽기 허용). 토큰은 캐시하지 않습니다. RSA 2048~8192비트 개인 키, Linux `/proc/self/fd`와 openssl이 필요하며 키와 상위 디렉터리를 보호해야 합니다.

App 환경변수가 하나도 없으면 기본 CLI는 gh를 사용합니다. runner와 orchestrator에서 `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID`, `GITHUB_APP_KEY_PATH` 중 하나라도 존재하면(빈 값 포함) `--github-app-read`가 필수이며, 누락 시 고정 오류로 종료하고 gh로 대체하지 않습니다. App 읽기 인증을 사용하려면 세 변수를 모두 로컬 프로세스 환경에 설정하세요. 키나 토큰을 명령 인자 또는 저장소에 넣지 마세요. 명시적 App 설정이 불완전해도 실패합니다. 토큰은 단일 허용 저장소에 대한 읽기 권한만 요청하고 Git diff fetch는 공개 저장소에서 익명으로만 수행합니다. fetch 전후 repo ID와 PR 상태 및 전체 SHA를 검증하고 리다이렉트를 거부하지만 저장소 이름 재사용 ABA 경쟁은 원자적으로 막지 못합니다. 전송과 제약은 `GITHUB_APP_TRANSPORT.md`를 참조하세요. 실제 설치 권한과 API 호환성은 검증되지 않았습니다. 일반 게시 경로의 격리 잠금은 유지되며 단일 VPS MVP만 별도 승인 게이트를 사용합니다. 테스트는 합성 키와 mock만 사용합니다.

## 제한 사항

localhost는 다른 로컬 사용자에 대한 인증 경계가 아닙니다. GitHub는 전달 및 이벤트 헤더가 아니라 본문에 서명합니다. 정확히 동일한 본문은 큐 행 또는 삭제 시 남긴 SHA-256 tombstone으로 중복 제거합니다. DB를 삭제하거나 오래된 백업으로 복원하면 그 이후의 중복 방지 기록이 사라져 재전송 공격이 가능해집니다. 정당하게 동일한 본문도 하나로 합쳐지며, 서명되지 않은 이벤트 헤더로는 이벤트의 출처를 입증할 수 없습니다. 행 수 제한은 큐에 저장된 본문 바이트 수만 제한하며 SQLite 오버헤드, 워커 결과, 이미 지나치게 커진 데이터베이스, HTTP 스레드 또는 파일 시스템 사용량은 제한하지 않습니다. 큐가 가득 차면 운영자의 신중한 개입이 필요하며, 이 과정에서 재전송 공격 방어가 약해질 수 있습니다. SQLite가 경로를 다시 열기 때문에 데이터베이스 디렉터리는 비공개로 유지해야 하며, 사이드카 파일과 백업도 보호해야 합니다. HTTP에는 TLS가 없으며 내장 서버와 SQLite 큐는 인터넷 노출, 악의적인 로컬 클라이언트 또는 대량 트래픽에 대비해 보안 강화되어 있지 않습니다. 실제 GitHub 웹훅은 localhost에 직접 도달할 수 없으며, 이 프로토타입을 공개적으로 노출해서는 안 됩니다. 프로젝트 자체는 인바운드 트래픽을 생성하지 않습니다.
