# Continuous dry-run worker

The resolver requires active profile `prreview` and uses normal Hermes authentication for `gpt-6.1-terra`. This is not a security sandbox; credentials may fall back to shared state. Dry-run stores reviews locally and is not offline. The CLI uses gh only when no App environment variables exist; otherwise `--github-app-read` is required, including for empty variables. Follow README.md for scratch and authentication setup.

Startup returns `isolation_unavailable` if the required profile or model client is unavailable. Earlier failures produce an argument error or `error`. Explicit inference and wiki-transfer approvals remain required.

```
python orchestrator.py --db /path/to/queue.db --wiki /path/to/wiki --repos /path/to/repos.json \
  --dry-run --enable-direct-inference --authorize-wiki-transfer
```

To additionally send Discord messages, configure `DISCORD_CHANNEL_ID` and `DISCORD_BOT_TOKEN` in the process environment and add `--enable-discord-notifications`. This is an external write, even in dry-run mode. Do not put credentials in command arguments or source. Notices contain the event and validated repository ID, name and PR number, but no title or review contents. Identity remains in each outbox event after queue cleanup. Missing identity is recovered only when its queue body matches the current repository allowlist; unresolved or untrusted identity is held, and invalid identity is marked failed without sending. Discord mentions are disabled. Repository names are limited to 200 ASCII characters and IDs and PR numbers to positive signed 64-bit integers. Events are stored transactionally in the queue database. Jobs claimed with notifications disabled are suppressed and are not sent when notifications are enabled later. A separate polling thread delivers them while reviews run. The outbox is durable and uses a 60-second lease and at most three attempts, with 30/60-second backoff. Expired leases are retried; exhausted events remain `failed` for operator inspection. The outbox is not automatically pruned and needs disk monitoring. Retry can reorder events. Discord does not provide an exactly-once guarantee: a crash or timeout after a successful POST can produce duplicates. Consult the local database for authoritative results; protect the database and backups.

The receiver never automatically cleans up queue items, including old `skipped` and `failed` jobs. At capacity, new deliveries return HTTP 503 while duplicates remain recognized; monitor queue capacity and disk usage. Use the offline retention procedure in RETENTION.md only for eligible `done` results. Failed, skipped, legacy, and otherwise ineligible results remain retained and require operator investigation; the provided cleanup function cannot remove them.

The loop backs off on worker errors, polls when idle, and handles SIGINT/SIGTERM by finishing the current operation before stopping. Adapter calls may take time to finish. Per-job retry scheduling is persisted by the worker. Logs contain statuses only, not exception text or review contents.

## Explicit single-VPS MVP publication

Only `juny0955/pr-review-bot` is permitted, and the repo configuration must contain exactly that enabled repository with its actual numeric ID. Configure the GitHub App read settings described in GITHUB_APP_TRANSPORT.md, plus the same WEBHOOK_SECRET as the receiver. The App must have pull request write permission; each publication token is narrowed to one repository and pull_requests write. Do not put credentials on the command line. Enable deliberately by replacing `--dry-run` with `--single-vps-publish --github-app-read --publication-ledger /private/ledger.db --publication-gate /private/gate`. No service is enabled by these instructions.

Create an owner-only gate directory and a mode 0600 regular `lock` file; parent directories must not be group/world writable. Use `revocation_gate.update_gate(path, policy, approvals, expected=...)` to administer state (see revocation_gate.py). Policy maps the decimal repo ID string to its exact name. Manual mode approves `[repo_id, repo_name, pr_number, head_sha, base_sha, sha256_utf8_review_hex]` after inspection. Alternatively, explicit preauthorization passes `auto_repos={"<actual repo ID>": "juny0955/pr-review-bot"}` to `update_gate` with that same ID/name in policy; no per-review approval is then required. This is a separate opt-in, restricted to the single-VPS MVP. An omitted or empty `auto_repos` disables automatic policy; every update replaces the entire state. Use `gate_snapshot` and its version for subsequent compare-and-swap updates, including revocation; remove auto policy and any manual approvals to stop all publication. Approval in manual mode is exact-content and revision specific. A signature saved by the updated receiver is rechecked before publication; older queued jobs without one cannot publish. Protect queue, gate, key, ledger and backups; a shared VPS account can modify all of them and is not an independent security boundary.

Discord outbox events describe review processing, not confirmed GitHub publication. Publication outcomes are logged as statuses; no publication-completed or publication-failed Discord outbox events are produced. Ambiguous claims are rechecked with per-job exponential backoff (starting at the poll interval, default 5 seconds, capped at 300 seconds); backoff resets on restart. Each reconciliation scans at most three pages (30 reviews) and starts no further page after five seconds. The five-second budget is checked only between calls and cannot interrupt an in-flight GET. The GitHub transport has a 15-second supervision deadline per request, and authentication can require separate requests; the exclusive gate remains held throughout reconciliation, so revocation waits for it or times out acquiring the gate. Neither the five-second budget nor transport cleanup is a hard wall-clock lock deadline. Markers beyond the first 30 reviews require operator reconciliation. Only a positive marker can establish delivery and no ambiguous POST is retransmitted. Ambiguous status is logged once per job until resolved or restart. Persistent ambiguity, stale PRs, missing signatures, or unavailable authorization require operator inspection; no automatic alert is sent. Results are not automatically removed. At 1,000 retained rows, new deliveries can receive 503; monitor capacity and use the bounded offline procedure in RETENTION.md for eligible results.

The gate uses one exclusive advisory flock across authorization, live PR checks, ledger operations and POST; gate updates and revocations wait for an in-flight publication, and a lock timeout fails closed. All cooperating administrators and publishers must use the same gate and lock file; same-account processes can bypass it. The general publication path remains locked by the isolation guard; only the explicitly enabled single-VPS MVP uses this gate. Per-job exceptions emit only a fixed publication_error once until that job recovers or disappears; polling and ledger protections continue. Publication rechecks the live PR and repository identity and head/base, and maintains a durable ledger. Preserve the ledger across restarts and backups: deleting or rolling it back can duplicate reviews. A failed or uncertain POST is never automatically retried; inspect GitHub and ledger manually. Signed webhook bodies can be replayed after database loss; signatures do not authenticate delivery IDs. Prompt instructions and secret patterns cannot prove wiki content or secrets are absent. See PRREVIEW_ISOLATION.md for disclosure and single-account risks.

At first claim the worker binds the delivery ID, webhook body hash and both job modes with a WEBHOOK_SECRET HMAC. Configure the same nonempty WEBHOOK_SECRET for the receiver, orchestrator and one-shot runner even in dry-run mode. Without it, a first claim can run but its provenance is missing, so retries, notification delivery and retention stay held; restoring the secret does not repair that claim. Retry and notification delivery require the same secret, the original queue body, and valid mode provenance; missing or invalid provenance stays held. Enabled publication also verifies the original webhook signature. Rotating the secret makes existing provenance unverifiable. This prevents a database-only mode flip without the secret, not an attack by the same UID: the worker can read the secret and same-account processes can bypass checks or modify results. Notifications wait for an explicit per-job mode; disabled jobs are suppressed rather than sent later, and legacy jobs without a mode remain held.
