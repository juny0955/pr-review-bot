# Continuous dry-run worker

The resolver requires active profile `prreview` and uses normal Hermes authentication for `gpt-6.1-terra`. This is not a security sandbox; credentials may fall back to shared state. Dry-run stores reviews locally and is not offline. The CLI uses gh only when no App environment variables exist; otherwise `--github-app-read` is required, including for empty variables. Follow README.md for scratch and authentication setup.

Startup returns `isolation_unavailable` if the required profile or model client is unavailable. Earlier failures produce an argument error or `error`. Explicit inference and wiki-transfer approvals remain required.

```
python orchestrator.py --db /path/to/queue.db --wiki /path/to/wiki --repos /path/to/repos.json \
  --dry-run --enable-direct-inference --authorize-wiki-transfer
```

To additionally send Discord messages, configure `DISCORD_CHANNEL_ID` and `DISCORD_BOT_TOKEN` in the process environment and add `--enable-discord-notifications`. This is an external write, even in dry-run mode. Do not put credentials in command arguments or source. Notices contain the event and validated repository ID, name and PR number, but no title or review contents. Identity remains in each outbox event after queue cleanup. Missing identity is recovered only when its queue body matches the current repository allowlist; unresolved or untrusted identity is held, and invalid identity is marked failed without sending. Discord mentions are disabled. Repository names are limited to 200 ASCII characters and IDs and PR numbers to positive signed 64-bit integers. They are stored transactionally in the queue database even while notifications are disabled; enabling notifications later sends the backlog. A separate polling thread delivers them while reviews run. The outbox is durable and uses a 60-second lease and at most three attempts, with 30/60-second backoff. Expired leases are retried; exhausted events remain `failed` for operator inspection. The outbox is not automatically pruned and needs disk monitoring. Retry can reorder events. Discord does not provide an exactly-once guarantee: a crash or timeout after a successful POST can produce duplicates. Consult the local database for authoritative results; protect the database and backups.

At capacity, a terminal queue item is eligible for cleanup only after all its outbox events are `sent`; pending, sending, failed, and other unsent events retain the source body and work result, regardless of identity. Recover or resolve failed and held events before cleanup. If notifications are disabled or the backlog cannot be delivered, the queue can fill and new deliveries return HTTP 503; monitor queue capacity and outbox status as well as disk usage.

The loop backs off on worker errors, polls when idle, and handles SIGINT/SIGTERM by finishing the current operation before stopping. Adapter calls may take time to finish. Per-job retry scheduling is persisted by the worker. Logs contain statuses only, not exception text or review contents.

## Explicit single-VPS MVP publication

Only `juny0955/pr-review-bot` is permitted, and the repo configuration must contain exactly that enabled repository with its actual numeric ID. Configure the GitHub App read settings described in GITHUB_APP_TRANSPORT.md, plus the same WEBHOOK_SECRET as the receiver. The App must have pull request write permission; each publication token is narrowed to one repository and pull_requests write. Do not put credentials on the command line. Enable deliberately by replacing `--dry-run` with `--single-vps-publish --github-app-read --publication-ledger /private/ledger.db --publication-gate /private/gate`. No service is enabled by these instructions.

Create an owner-only gate directory and a mode 0600 regular `lock` file; parent directories must not be group/world writable. Use `revocation_gate.update_gate(path, policy, approvals, expected=...)` to administer state (see revocation_gate.py). Policy maps the decimal repo ID string to its exact name. Manual mode approves `[repo_id, repo_name, pr_number, head_sha, base_sha, sha256_utf8_review_hex]` after inspection. Alternatively, explicit preauthorization passes `auto_repos={"<actual repo ID>": "juny0955/pr-review-bot"}` to `update_gate` with that same ID/name in policy; no per-review approval is then required. This is a separate opt-in, restricted to the single-VPS MVP. An omitted or empty `auto_repos` disables automatic policy; every update replaces the entire state. Use `gate_snapshot` and its version for subsequent compare-and-swap updates, including revocation; remove auto policy and any manual approvals to stop all publication. Approval in manual mode is exact-content and revision specific. A signature saved by the updated receiver is rechecked before publication; older queued jobs without one cannot publish. Protect queue, gate, key, ledger and backups; a shared VPS account can modify all of them and is not an independent security boundary.

Discord outbox events describe review processing, not confirmed GitHub publication. Publication outcomes are logged as statuses; no publication-completed or publication-failed Discord outbox events are produced. In particular an ambiguous POST is not proof of failure and requires operator reconciliation.

The gate uses one exclusive advisory flock across authorization, live PR checks, ledger operations and POST; gate updates and revocations wait for an in-flight publication, and a lock timeout fails closed. All cooperating administrators and publishers must use the same gate and lock file; same-account processes can bypass it. The general publication path remains locked by the isolation guard; only the explicitly enabled single-VPS MVP uses this gate. Per-job exceptions emit only a fixed publication_error once until that job recovers or disappears; polling and ledger protections continue. Publication rechecks the live PR and repository identity and head/base, and maintains a durable ledger. Preserve the ledger across restarts and backups: deleting or rolling it back can duplicate reviews. A failed or uncertain POST is never automatically retried; inspect GitHub and ledger manually. Signed webhook bodies can be replayed after database loss; signatures do not authenticate delivery IDs. Prompt instructions and secret patterns cannot prove wiki content or secrets are absent. See PRREVIEW_ISOLATION.md for disclosure and single-account risks.
